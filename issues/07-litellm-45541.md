## Problem

`Logging.post_call` keeps a full serialized copy of every provider response in `model_call_details
["original_response"]` for the life of the request even when nothing reads it — the largest per-request allocation
LiteLLM adds:

- a 16 MiB base64 image response leaves a ~22.4 MB string held after `post_call` returns;
- a 256 × 3072 float embedding batch is ~17 MB.

For dict responses, `post_call` even builds the copy with `json.dumps` (`litellm_logging.py`, top of `post_call`),
so it is created, not just referenced. OpenAI/Azure image-gen hits this path (sync handlers pass
`raw_response.parse().model_dump()`; async handlers pre-stringify the same way).

Known readers (all opt-in):
- `integrations/opentelemetry.py` `set_raw_request_attributes`
- `integrations/arize/_utils.py` (fallback output)
- `proxy/guardrails/guardrail_hooks/cisco_ai_defense/cisco_ai_defense_mcp.py`
- `logger_fn` / dynamic input callbacks (receive `model_call_details`)

## Approach

1. Clone `BerriAI/litellm` (see issue 05 for setup).
2. Read `litellm/litellm_logging.py` `post_call`; identify when `original_response` is actually consumed.
3. Design options: lazily compute the serialized copy only when a reader is registered (opentelemetry/arize/
   cisco hooks/`logger_fn` present), or drop it / store a reference instead of `json.dumps`.
4. Keep behavior identical when any opt-in reader IS active (guard against silently breaking OTel raw attributes).
5. Measure before/after with the sizes given in the issue (16 MiB image, big embedding batch).
